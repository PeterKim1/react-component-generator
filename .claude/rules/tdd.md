# TDD Rule

> **이 규칙은 Rigid다. 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"로 처리하지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 프로젝트 규칙이 없을 때 쓰는 **기본값(fallback)** 이다.
- 두 규칙이 충돌하면 프로젝트 규칙을 따르고, 충돌하지 않는 부분은 이 파일을 적용한다.

## 적용 기준

### TDD를 반드시 적용한다

- 비즈니스 로직
- API (엔드포인트, 핸들러, 외부 호출 래퍼)
- 유틸리티 / 순수 함수
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성한다)
- 상태·분기가 있는 훅과 컴포넌트 동작

### TDD가 불필요하다

- 타입 정의
- 설정 파일
- 순수 UI (스타일, 레이아웃, 정적 마크업)
- SQL / 마이그레이션 스크립트

판단이 애매하면 **적용 대상으로 취급**한다.

## RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트 이름은 기대 동작을 문장으로 쓴다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 잘못된 셋업으로 인한 실패는 RED가 아니므로 테스트를 고친 뒤 다시 실행한다.
- 처음부터 통과하는 테스트는 아무것도 검증하지 못한다. 테스트를 고친다.

### GREEN: 최소한의 구현

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 지금 테스트가 요구하지 않는 분기, 옵션, 추상화를 넣지 않는다.
- 실행해서 **신규 테스트와 기존 테스트가 모두 통과**하는지 확인한다. 기존 테스트가 깨지면 GREEN이 아니다.

### REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지**한다. 변경마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 RED로 돌아간다.

### 반복

- 다음 동작이 남아 있으면 **RED로 돌아간다.** 한 번에 여러 동작을 구현하지 않는다.

## 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다면 **그 코드를 삭제하고 RED부터 다시 시작한다.**
- **"참고용"으로 남기는 것도 금지**한다. 주석 처리, 별도 파일 보관, 기억에 의존한 재작성 모두 해당한다.
- 삭제 후에는 테스트가 요구하는 것만 새로 작성한다.

## 변명 차단표

| 변명 | 반론 |
| --- | --- |
| "너무 단순해서 테스트가 불필요하다" | 단순한 코드는 테스트도 단순하다. 비용이 거의 없고, 단순한 코드가 가장 자주 조용히 깨진다. |
| "나중에 테스트를 추가하겠다" | 나중에 쓴 테스트는 구현을 그대로 따라 쓰게 되어 버그를 잡지 못한다. 나중은 오지 않는다. |
| "시간이 없다" | 디버깅과 회귀 수정이 테스트 작성보다 오래 걸린다. 시간이 없을수록 RED로 범위를 좁힌다. |
| "삭제하면 낭비다" | 매몰 비용이다. 테스트 없이 검증되지 않은 코드를 유지하는 비용이 재작성 비용보다 크다. |
| "프로토타입이다" | 프로토타입은 그대로 프로덕션이 된다. 버릴 코드라면 테스트도 필요 없지만, 그 경우 병합하지 않는다. |
