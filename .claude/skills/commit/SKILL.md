# Commit

변경사항을 분석해 컨벤션에 맞는 한국어 커밋 메시지로 커밋한다. 별도의 승인 절차 없이 바로 커밋한다.

## 절차

### 1. 변경사항 분석

아래를 실행해 현재 상태를 파악한다. 서로 독립적이므로 한 번에 병렬로 실행한다.

- `git status` — 변경·추가·삭제된 파일과 untracked 파일
- `git diff` — 스테이징되지 않은 변경
- `git diff --staged` — 이미 스테이징된 변경
- `git log --oneline -10` — 기존 메시지 스타일 확인

git 저장소가 아니면(`not a git repository`) 커밋하지 말고 그 사실을 알린다. `git init`은 사용자가 요청할 때만 한다.

변경이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.

diff가 크면 파일 목록과 `git diff --stat`으로 윤곽을 잡은 뒤 필요한 파일만 자세히 읽는다.

### 2. 논리적 단위로 분류

변경을 **하나의 목적**을 가진 묶음으로 나눈다.

- 한 커밋에는 한 가지 이유만 담는다. 기능 추가와 무관한 리팩터링, 설정 변경은 분리한다.
- 서로 의존하는 파일(구현 + 해당 테스트, 컴포넌트 + 스타일)은 같은 커밋에 둔다.
- 의존성 변경(`package.json`, lock 파일)은 그것을 쓰는 기능과 함께 묶거나, 독립적이면 `chore`로 분리한다.
- 하나의 파일 안에 서로 다른 목적의 변경이 섞여 있으면 사용자에게 알리고 나눌지 묻는다. 대화형 스테이징(`git add -p`, `-i`)은 쓰지 않는다.
- 변경이 한 목적뿐이면 커밋 하나로 충분하다. 억지로 쪼개지 않는다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>

Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>
```

**type**

| type | 용도 |
| --- | --- |
| `feat` | 사용자가 체감하는 새 기능·UI 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `chore` | 빌드, 설정, 의존성, 문서 등 코드 동작과 무관한 작업 |

**작성 규칙**

- 요약은 한국어로, 50자 안팎의 한 줄. 마침표를 붙이지 않는다.
- "무엇을 했는지"가 아니라 "무엇이 달라졌는지"를 쓴다. 예: `feat: 결과 카드에 코드 복사 버튼 추가`
- 본문은 **왜** 바꿨는지가 diff만으로 드러나지 않을 때만 쓴다. 한 줄에 72자 안팎으로 줄바꿈한다.
- 코드 식별자, 파일명, 라이브러리 이름은 원문 그대로 쓴다.
- 이 저장소의 기존 로그가 위 형식과 다른 스타일(예: scope 사용)을 쓰고 있다면 기존 스타일을 따른다.
- 마지막 줄에는 위 `Co-Authored-By` 트레일러를 붙인다.

### 4. 커밋 실행

사용자 승인을 기다리지 않고 바로 커밋한다. 커밋 단위마다 다음을 수행한다.

1. 해당 파일만 이름으로 지정해 `git add <파일...>` (`git add .`, `git add -A`는 쓰지 않는다)
2. 메시지는 heredoc으로 전달해 `git commit`

모든 커밋이 끝나면 `git status`와 `git log --oneline`으로 결과를 확인하고, 만든 커밋 목록(해시, 메시지, 포함 파일)을 사용자에게 보고한다.

다만 2단계 분류에서 한 파일 안에 서로 다른 목적의 변경이 섞여 있어 나누는 기준이 모호하면, 임의로 판단하지 말고 사용자에게 묻는다.

## 주의

- `push`는 하지 않는다. 사용자가 따로 요청할 때만 한다.
- `--no-verify`, `--amend`, `reset --hard` 등 이력을 바꾸거나 검사를 건너뛰는 옵션은 쓰지 않는다. 훅이 실패하면 원인을 고쳐 새 커밋을 만든다.
- 비밀 정보(`.env`, API 키, 인증서)나 빌드 산출물(`dist/`, `node_modules/`)이 포함되어 있으면 커밋 대상에서 빼고 사용자에게 알린다.
